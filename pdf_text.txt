1. Project Overview 
Scenario 
A real-estate analytics start-up predicts asking prices (in ₹ lakhs) for property listings. New batches of listings arrive 
regularly, and today every retraining and release is done by hand, with no record of which data or code produced 
which model. 
The start-up wants a fully automated pipeline: data in, features built, model trained and validated, registered, 
deployed and monitored. The pipeline must also stop cleanly, keeping the previous model in service, when data or 
model quality is not acceptable. 
Your role 
You are the lead MLOps engineer. You design the system, build it and present it to the founders. 
Working mode 
Work in pairs.

5. Project Tasks 
Each task states the outcome you must achieve and how it will be judged. How you achieve it is your design decision. 
Task 1: Problem framing and lifecycle map   (Topic 1) 
What you must achieve 
Define the business objective, the success metrics (an error metric plus a plain-language interpretation for the 
founders) and the non-functional requirements such as prediction latency and how fresh the model must be. 
Draw the system architecture and map it to the MLOps lifecycle. 
Acceptance criteria 
• A design note of at most two pages with an architecture diagram. 
• Success thresholds are numeric and justified. 
• Every architecture component is traceable to a lifecycle stage. 
Task 2: Configuration, code and data management   (Topics 4, 10) 
What you must achieve 
Make one YAML configuration the single source of truth for the pipeline, and put code, configuration and data under 
version control so any result can be reproduced. 
Acceptance criteria 
• A fresh clone reproduces the reported metrics within a stated tolerance. 
• No paths, thresholds or hyperparameters are hard-coded. 
• Configurations are validated on load. 
Task 3: Pipeline design   (Topics 13, 15) 
What you must achieve 
Implement the pipeline as an orchestrated workflow with separate stages: ingest, validate data, build features, train, 
evaluate, register, deploy and monitor. 
Each stage must have defined inputs and outputs and must be re-runnable on its own. 
Acceptance criteria 
• A diagram of the workflow graph is provided and matches the code. 
• Stage-level logs and a run history are available. 
• Any single stage can be re-run without repeating the whole pipeline. 
Task 4: Validation gates and safe failure   (Topic 15) 
What you must achieve 
Add a data gate (for example schema, value ranges and a limit on missing values) and a model gate (a quality 
threshold plus a comparison against the current production model). 
When a gate fails, the pipeline must stop cleanly with an explanatory message and the previous production model 
must keep serving. 
Acceptance criteria 
• At least two failing scenarios are demonstrated: a bad data batch and a model below the threshold. 
• The production model and endpoint are unchanged after each failure. 
• Gate thresholds are configurable and justified.

Task 5: Tracking, registry and lineage   (Topic 15) 
What you must achieve 
Track every run, register models with stage transitions, and make lineage traceable: from a deployed model you must 
be able to find the code version, data version, configuration and run that produced it. 
Acceptance criteria 
• A live lineage demonstration starting from the deployed model. 
• Stage transitions in the registry happen only through the pipeline. 
• Run records include data version and configuration. 
Task 6: Automated build and release   (Topic 2) 
What you must achieve 
A pull request must trigger tests and a lightweight pipeline run. A merge to the main branch must build a deployable 
image and release the new version. Document how to roll back to the previous version. 
Acceptance criteria 
• CI history shows a passing and a failing pull request and at least one release. 
• The image is tagged so that a running container can be linked to a commit. 
• The rollback procedure is written and tested once. 
Task 7: Serving and monitoring   (Topics 6, 7) 
What you must achieve 
Serve the production model as a containerised API with operational metrics: latency, throughput, errors and the 
distribution of predicted prices. 
Process the incoming batches to measure data drift and, because prices are supplied, performance drift. Define alert 
conditions and show which batches trigger them. 
Acceptance criteria 
• A dashboard or report shows operational metrics and drift over the three batches. 
• Alert thresholds are justified, and the batches that trigger them are identified with evidence. 
• You explain what the pipeline should do when an alert fires. 
Task 8: Final demonstration   (Topics 1, 2, 7, 15) 
What you must achieve 
Present the full loop live or as a recording: a code change, the CI run, the pipeline run, deployment and the 
monitoring update, followed by one failure scenario. 
Acceptance criteria 
• The demonstration lasts 5 to 10 minutes. 
• Every team member explains a part of the system. 
• The failure scenario shows safe behaviour.

7. Rules & Constraints 
• Use only free tools and free-tier resources. 
• Every stage must be automated. Manual copying of files between stages is not allowed. 
• Only the pipeline may change the production model. 
• Each team member must have commits in the repository; individual contributions are checked. 
• No secrets or credentials may be committed to the repository. 
8. Academic Integrity 
This is a two-person project. Work submitted under your names must be work you and your partner did and can 
explain. 
• Do not copy another group's repository, code, configuration, dashboard, or report, in whole or in part. Two 
submissions that are substantially the same will both be investigated, regardless of which group worked first. 
• During the demonstration, both partners must be able to explain, modify live, and justify every part of the 
submission without reading from notes you did not write yourselves. An inability to do this is treated as 
evidence the work is not your own. 
• Reusing a prior year's submission, a public GitHub repository, or another course's project as a starting point is 
not allowed unless you cite it explicitly and your own contribution is clearly separated from it. 
• Violations are treated as an academic integrity case under your institute's policy, not simply as a grading 
deduction.
