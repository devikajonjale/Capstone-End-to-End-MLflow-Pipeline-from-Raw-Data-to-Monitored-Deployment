[8] 1. Project Overview
[9] Scenario
[10] A real-estate analytics start-up predicts asking prices (in ₹ lakhs) for property listings. New batches of listings arrive regularly, and today every retraining and release is done by hand, with no record of which data or code produced which model.
[11] The start-up wants a fully automated pipeline: data in, features built, model trained and validated, registered, deployed and monitored. The pipeline must also stop cleanly, keeping the previous model in service, when data or model quality is not acceptable.
[12] Your role
[13] You are the lead MLOps engineer. You design the system, build it and present it to the founders.
[14] Working mode
[15] Work in pairs.

[127] 5. Project Tasks
[128] Each task states the outcome you must achieve and how it will be judged. How you achieve it is your design decision.
[129] Task 1: Problem framing and lifecycle map   (Topic 1)
[130] What you must achieve
[131] Define the business objective, the success metrics (an error metric plus a plain-language interpretation for the founders) and the non-functional requirements such as prediction latency and how fresh the model must be.
[132] Draw the system architecture and map it to the MLOps lifecycle.
[133] Acceptance criteria
[134] A design note of at most two pages with an architecture diagram.
[135] Success thresholds are numeric and justified.
[136] Every architecture component is traceable to a lifecycle stage.
[137] Task 2: Configuration, code and data management   (Topics 4, 10)
[138] What you must achieve
[139] Make one YAML configuration the single source of truth for the pipeline, and put code, configuration and data under version control so any result can be reproduced.
[140] Acceptance criteria
[141] A fresh clone reproduces the reported metrics within a stated tolerance.
[142] No paths, thresholds or hyperparameters are hard-coded.
[143] Configurations are validated on load.
[144] Task 3: Pipeline design   (Topics 13, 15)
[145] What you must achieve
[146] Implement the pipeline as an orchestrated workflow with separate stages: ingest, validate data, build features, train, evaluate, register, deploy and monitor.
[147] Each stage must have defined inputs and outputs and must be re-runnable on its own.
[148] Acceptance criteria
[149] A diagram of the workflow graph is provided and matches the code.
[150] Stage-level logs and a run history are available.
[151] Any single stage can be re-run without repeating the whole pipeline.
[152] Task 4: Validation gates and safe failure   (Topic 15)
[153] What you must achieve
[154] Add a data gate (for example schema, value ranges and a limit on missing values) and a model gate (a quality threshold plus a comparison against the current production model).
[155] When a gate fails, the pipeline must stop cleanly with an explanatory message and the previous production model must keep serving.
[156] Acceptance criteria
[157] At least two failing scenarios are demonstrated: a bad data batch and a model below the threshold.
[158] The production model and endpoint are unchanged after each failure.
[159] Gate thresholds are configurable and justified.
[160] Task 5: Tracking, registry and lineage   (Topic 15)
[161] What you must achieve
[162] Track every run, register models with stage transitions, and make lineage traceable: from a deployed model you must be able to find the code version, data version, configuration and run that produced it.
[163] Acceptance criteria
[164] A live lineage demonstration starting from the deployed model.
[165] Stage transitions in the registry happen only through the pipeline.
[166] Run records include data version and configuration.
[167] Task 6: Automated build and release   (Topic 2)
[168] What you must achieve
[169] A pull request must trigger tests and a lightweight pipeline run. A merge to the main branch must build a deployable image and release the new version. Document how to roll back to the previous version.
[170] Acceptance criteria
[171] CI history shows a passing and a failing pull request and at least one release.
[172] The image is tagged so that a running container can be linked to a commit.
[173] The rollback procedure is written and tested once.
[174] Task 7: Serving and monitoring   (Topics 6, 7)
[175] What you must achieve
[176] Serve the production model as a containerised API with operational metrics: latency, throughput, errors and the distribution of predicted prices.
[177] Process the incoming batches to measure data drift and, because prices are supplied, performance drift. Define alert conditions and show which batches trigger them.
[178] Acceptance criteria
[179] A dashboard or report shows operational metrics and drift over the three batches.
[180] Alert thresholds are justified, and the batches that trigger them are identified with evidence.
[181] You explain what the pipeline should do when an alert fires.
[182] Task 8: Final demonstration   (Topics 1, 2, 7, 15)
[183] What you must achieve
[184] Present the full loop live or as a recording: a code change, the CI run, the pipeline run, deployment and the monitoring update, followed by one failure scenario.
[185] Acceptance criteria
[186] The demonstration lasts 5 to 10 minutes.
[187] Every team member explains a part of the system.
[188] The failure scenario shows safe behaviour.
